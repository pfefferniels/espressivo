# W1 adversarial panel — full findings (4 lenses, 2026-08-09)

Raw panel output, verbatim. Adjudication in LOG.md.


## Lens: feasibility

**Verdict:** SOUND-WITH-FIXES — D-A survives as a mechanism but not as written. The mechanism is verified correct: `attribute(name, el).setValue(...)` mutates only `Attribute._value` (XomTypes.ts:218-220) while `Element.toXML` walks `_attributes` front-to-back (:773-775), so it IS order-preserving, and `Element.addAttribute` does remove-then-push and DOES move an existing attribute to the end (:492-500, measured: `date bpm beatLength` → `date beatLength bpm`) — SURVEY.md:3618-3626 is exactly right, and `attribute()` (tree.ts:400-413) returns the live attribute so writes reach the serializer. Locating maps and defs from the raw tree is cheap and the style-def lookup for RESOLVED-1's centers is a single O(n) forward pass per map with a pre-indexed header (sketch in finding 5's fix). What does not survive is the framing around the mechanism. First, the def parsers are not \"triggered by reaching a header through the ordinary APIs\" — they run inside `new Mpm(text)` itself, unconditionally, via Header.parseData's eager `addStyleType` loop, so D-A's \"never itself instantiates them\" clause promises a relief that does not exist; only a full-raw `new Builder().build(text)` path (verified non-mutating, whitespace and def attributes intact) actually avoids it. Second, `GenericMap.parseData` ends in an unconditional `sortXml()` that reorders map children, exiles dateless children to the end, and — because `insertChild` splices into a node list containing Text — hoists every instruction in front of all whitespace; that is a structural parse mutation DESIGN.md never records. Third, and decisively, Tier 2 must go: `Element.toXML` re-emits `xmlns` on every namespaced element and `Element.wrap` drops the source declarations, so `parse→serialize` inflates a real Tier-2-eligible fixture from 2444 to 4011 bytes — strict `input == output` is unreachable for every MPM document regardless of what the applier does, and RubatoDef's present-attribute rewrite (`intensity=\"1.0\"` → `\"1\"`) independently breaks the exception predicate. Recommended disposition: keep D-A's write discipline verbatim, delete the \"never itself instantiates\" clause in favour of an explicit baseline-mutations list, restate Tier 2 as structural rather than byte equality (and amend CAMPAIGN.md invariant 6 to match), pin the style-scope rule to the positional `findStyleSwitchAt` semantics, and make RESOLVED-1's center population an explicit algorithm before any of §8's sampling bounds are trusted.

### [BLOCKER] Tier 2 (strict input==output bytes) is unreachable for EVERY MPM document, not just def-bearing ones — the serializer re-emits xmlns on every element

- **Claim:** DESIGN.md:220-224 and ✔ RESOLVED-3 (DESIGN.md:504-508) contract strict `input == output` bytes for "documents that carry no self-mutating def". No document can satisfy it. `Element.wrap` DROPS all `xmlns`/`xmlns:*` attributes at parse (XomTypes.ts:410) and `Element.toXML` unconditionally re-emits a namespace declaration on every element that has a namespace URI, with no check for an inherited declaration (XomTypes.ts:766-771). `Document.toXML` also rewrites the XML declaration (XomTypes.ts:836-838). Since every valid MPM binds the default MPM namespace, parse→serialize always inflates and never matches. Measured on a fixture that RESOLVED-3 explicitly declares Tier-2-eligible (no rubatoDef at all; its accentuationPatternDef DOES carry @length): tests/integration/fixtures/all-maps-reference/all_maps.mpm round-trips 2444 bytes → 4011 bytes (+64%), `<?xml version="1.0"?>` → `<?xml version="1.0" encoding="UTF-8"?>`, and `<performance ...>` → `<performance xmlns="http://www.cemfi.de/mpm/ns/1.0" ...>`. The same holds for a hand-built document with zero defs and zero maps. CAMPAIGN.md:50-51 invariant 6 ("s=1 is byte-identity … Property-tested") inherits the defect.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/xml/XomTypes.ts:410 (xmlns dropped at wrap), :766-771 (xmlns re-emitted per element in toXML), :836-838 (XML decl rewritten); DESIGN.md:220-224, DESIGN.md:504-508; CAMPAIGN.md:50-51; measured against /Users/nielspfeffer/Projects/meico-ts-exag/tests/integration/fixtures/all-maps-reference/all_maps.mpm
- **Proposed fix:** Delete Tier 2, or restate it as a STRUCTURAL equality (same element tree, same attribute set, same attribute order, same attribute values) rather than a byte equality — a comparison the applier can actually satisfy and that still catches the failure Tier 2 was invented to catch. Keep Tier 1 (`exaggerate(mpm,{})` bytes == `parse→serialize(mpm)` bytes) as the only byte contract, and fix CAMPAIGN.md invariant 6 to say "canonical-baseline identity", not "byte-identical document".

### [MAJOR] RESOLVED-3's "self-mutating def" predicate is wrong on its own terms: RubatoDef rewrites attributes that ARE present

- **Claim:** RESOLVED-3 (DESIGN.md:504-508) defines the Tier-2 exception set as "`rubatoDef` with an omitted `intensity`/`lateStart`/`earlyEnd`, `accentuationPatternDef` with an omitted `@length`". But `RubatoDef.parseDataInternal` also rewrites values that are physically present: the else-branch at RubatoDef.ts:47-55 does `intensityAttr.setValue(String(ensureIntensityBoundaries(parseJavaDouble(...))))`, and lines :70-73 unconditionally do `lateStartAttr.setValue(String(le.getKey()))` / `earlyEndAttr.setValue(String(le.getValue()))` whether or not the attributes were absent. Because the round-trip is `parseJavaDouble` → `String()`, every Java-meico-written literal loses its `.0`. Measured: `<rubatoDef name="r" frameLength="720.0" intensity="1.0" lateStart="0.0" earlyEnd="1.0"/>` (fully specified — Tier-2-eligible by the stated predicate) parses+serializes as `intensity="1" lateStart="0" earlyEnd="1"`. Java meico prints doubles as "1.0", so essentially every Java-produced rubatoDef diverges.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/mpm/elements/styles/defs/RubatoDef.ts:47-55 and :70-73; DESIGN.md:504-508 (RESOLVED-3 exception predicate); SURVEY.md:1394-1401 documents only the ADD case, so the design inherited an incomplete survey claim
- **Proposed fix:** If Tier 2 survives in any form, the predicate must be "contains no `rubatoDef` and no `accentuationPatternDef` at all, and no map whose children are not already in ascending @date order" (see the sortXml finding). Given the xmlns finding, the honest conclusion is to drop Tier 2 rather than repair the predicate, and to pin the divergence with a test that asserts the *value rewrite* as well as the *attribute addition*.

### [MAJOR] D-A's "never itself instantiates the def parsers" clause is decorative: the def parsers run in the Mpm CONSTRUCTOR, before any Dated/Header call

- **Claim:** D-A (DESIGN.md:206-212) says the module "never *itself* instantiates the def parsers that mutate the document on parse (RubatoDef, AccentuationPatternDef) … though reaching a header through the ordinary APIs can trigger them", and RESOLVED-3 (DESIGN.md:487-489) repeats "reaching a map through the Header/Dated APIs is already enough to trigger them". Both frame the trigger as conditional on API access. It is not conditional on anything: it is the constructor. `new Mpm(text)` → `Mpm.parseData` (Mpm.ts:113/116 → :137-151) → `Performance.createPerformance` → `Performance.parseData` (:210, `Global.createGlobal(globalElt)`) → `Global.parseData` (Global.ts:61, `Header.createHeader(headerElt)`) → `Header.parseData` (Header.ts:76-79) which EAGERLY queries every `*Styles` descendant and calls `addStyleType` (:106-129), constructing `RubatoStyle`/`MetricalAccentuationStyle` and therefore `RubatoDef.parseDataInternal` (RubatoDef.ts:44,49,61,66,72-73) and `AccentuationPatternDef.parseDataInternal` (:36-40, :67). Verified: constructing an Mpm and immediately calling `writeMpm()` — with no `getMap`, no `getHeader`, no `getDated` anywhere — already emits `intensity="1" lateStart="0" earlyEnd="1"` and `length="4"`. So the discipline D-A imposes on the applier buys exactly nothing, and an implementer reading D-A will reasonably believe a raw-XML applier preserves the document. It does not.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/mpm/Mpm.ts:113,116,137-151; src/mpm/elements/Performance.ts:187-220 (esp. :210); src/mpm/elements/Global.ts:52-75 (esp. :61); src/mpm/elements/Header.ts:72-80, :106-129; src/mpm/elements/styles/defs/RubatoDef.ts:41-73; src/mpm/elements/styles/defs/AccentuationPatternDef.ts:36-40; DESIGN.md:206-212, DESIGN.md:487-489
- **Proposed fix:** Two honest options, pick one and say so in D-A. (a) WEAKEN: delete the "never itself instantiates" clause and state plainly that `new Mpm(text)` is itself the mutation, that the canonical baseline is `parse→serialize`, and that the raw-XML rule exists only to avoid the *writer* APIs (ArticulationData round-trips, TemporalSpread.getXml materialization, GenericMap.addElement re-sorting) — which is a real and sufficient justification on its own. (b) GO FULL RAW: bypass `Mpm` entirely and build with `new Builder().build(text)` (XomTypes.ts:849-868). Verified non-mutating: rubatoDef attributes untouched and whitespace text nodes preserved. This is the only way to keep the document's def attributes and child order intact.

### [MAJOR] GenericMap construction DOES mutate the XML — sortXml() runs unconditionally at parse and relocates children (including whitespace)

- **Claim:** DESIGN.md never states that parsing a map rewrites the map element's children, and §7.9's write-mechanics note (DESIGN.md:803-806) claims only that a dateless child is "[left] in the document". `GenericMap.parseData` ends with an unconditional `this.sortXml()` (GenericMap.ts:157); `sortXml` (:167-174) does `xml.removeChild(e); xml.insertChild(e, i)` for each indexed element, where `i` is the ELEMENT index but `insertChild` splices into `_children`, which also holds Text nodes (XomTypes.ts:547-556). Three measured consequences: (1) a map whose `<tempo>` children are out of date order is REORDERED in the document at parse; (2) a child without `@date` is not merely skipped, it is MOVED TO THE END of the map; (3) in any pretty-printed document every instruction element is hoisted in front of all whitespace, which collects at the end of the map element — verified: a formatted `<tempoMap>` with two `<tempo>` children serializes as `<tempoMap><tempo/><tempo/>\n          \n          \n        </tempoMap>`. `AccentuationPatternDef.parseDataInternal` does the same for `<accentuation>` children (AccentuationPatternDef.ts:67). This answers question (3): yes, GenericMap construction mutates, and the mutation is structural, not just attribute-level.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/mpm/elements/maps/GenericMap.ts:157 (sortXml at end of parseData), :167-174 (sortXml body), :141-156 (skip rules); /Users/nielspfeffer/Projects/meico-ts-exag/src/xml/XomTypes.ts:547-556 (insertChild splices into the node list, not the element list); src/mpm/elements/styles/defs/AccentuationPatternDef.ts:67; DESIGN.md:803-806
- **Proposed fix:** Add map-child reordering and whitespace relocation to D-A/RESOLVED-3's list of baseline mutations. Then decide which child order is NORMATIVE for the applier: on an `Mpm`-parsed tree the raw walker sees the already-re-sorted order, on a `Builder`-parsed tree it sees source order. Since the renderer's style-switch scope is positional over the re-sorted order (see the findStyleSwitchAt finding), a full-raw applier MUST reproduce GenericMap.parseData's stable date ordering itself (backwards scan for the last index with date <= new date) before scanning for `<style>`, or it resolves names differently from the renderer.

### [MAJOR] The style-in-scope lookup the applier must replicate is index-based findStyleSwitchAt, not the public date-based getStyleAt; the two disagree at equal dates

- **Claim:** RESOLVED-1 (DESIGN.md:334-351) requires "instruction attributes with names resolved through the style in scope", but does not say which of two non-equivalent lookups the codebase offers is normative. The renderer uses `findStyleNameAt(index)` → `findStyleSwitchAt(index)` (GenericMap.ts:480-495), which scans BACKWARDS BY ARRAY POSITION from the instruction's index; this is what `TempoMap.getTempoDataOf` (TempoMap.ts:128) and `DynamicsMap.getDynamicsDataOf` (DynamicsMap.ts:160) call. The public `getStyleNameAt(date)`/`getStyleAt(date, type)` (GenericMap.ts:497-517) instead takes the last `<style>` whose date <= the argument. Concrete divergence: for `<dynamicsMap><dynamics date="0.0" volume="f"/><style date="0.0" name.ref="MEI export"/></dynamicsMap>` (parse preserves document order among equal dates, GenericMap.ts:148-155), the renderer resolves the instruction with NO style, so `DynamicsStyle.getNumericValueStatic("f", null)` falls through `parseFloat("f")` → NaN → 100.0 (DynamicsStyle.ts:49-56); `getStyleAt(0, dynamicsStyles)` returns the style and yields 97.0. An applier that used the public API would put 97 into the performance-wide geomean where the renderer uses 100, and would rewrite the def as if it governed a level it does not.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/mpm/elements/maps/GenericMap.ts:480-495 vs :497-517; src/mpm/elements/maps/TempoMap.ts:128-129; src/mpm/elements/maps/DynamicsMap.ts:160-161; src/mpm/elements/styles/DynamicsStyle.ts:49-56; src/mpm/elements/styles/TempoStyle.ts:49-58; DESIGN.md:334-351
- **Proposed fix:** Add to §7.1/§7.2 notes: "style scope is POSITIONAL over the date-stable child order, never date-based — replicate GenericMap.findStyleSwitchAt, never call getStyleAt." The raw lookup sketch that satisfies this: per environment, stable-sort the map's child elements by parseFloat(@date) preserving document order for ties; skip children without @date and `<style>` without `@name.ref`; walk once forward carrying `currentStyleName`; on a name-valued level, look `currentStyleName` up as `<styleDef @name>` under the environment's local `<header>/<{tempo|dynamics}Styles>` first and the global header second (whole-styleDef shadowing, GenericMap.ts:506-513 — NOT a per-def merge), then find the `<tempoDef|dynamicsDef @name=levelString>` child. O(total elements), one pass, no XPath.

### [MAJOR] RESOLVED-1's center population is under-determined in three ways, and §8's own dynamics derivation assumes a fourth reading

- **Claim:** RESOLVED-1 (DESIGN.md:337-343) defines the center as "the unweighted geometric mean of every *style-resolved* level value reachable in that performance — instruction attributes with names resolved through the style in scope, plus the def values themselves — computed with element-identity dedupe". Three questions this leaves open, each of which changes every number the transform writes: (i) do defs in an in-scope styleDef that NO instruction references join the population? (ii) element-identity dedupe cannot deduplicate a named level, because the instruction element and the def element are distinct — so a def referenced by N instructions contributes N resolved values PLUS its own value, i.e. named levels are reference-count-weighted while numeric levels are not, and a document mixing the two (numeric from mpmify, named from MEI export — SURVEY.md:882-887) gets a systematically biased center; (iii) an unresolvable placeholder (`volume="-"`, present in tests/integration/fixtures/reference/dynamics.mpm) resolves to 100.0 in the renderer (DynamicsStyle.ts:54-55) — does that 100.0 join the population? On dynamics.mpm the three readings give centers of ~94.8, ~90.2 and ~91.7. Worse, §8's dynamics row (DESIGN.md:881) derives its sampling bound from yet another rule — "A p(48)…f(97) map centers at ≈ 68", i.e. √(48·97), defs only and each once, no instruction occurrences — which RESOLVED-1's population never produces. The clamp-onset s ≈ 1.8 quoted there is therefore not the value the specified implementation would exhibit.
- **Evidence:** DESIGN.md:337-343 (RESOLVED-1 population), DESIGN.md:881 (§8 dynamics row, center ≈68 and s≈1.8); /Users/nielspfeffer/Projects/meico-ts-exag/src/mpm/elements/styles/DynamicsStyle.ts:49-56; /Users/nielspfeffer/Projects/meico-ts-exag/tests/integration/fixtures/reference/dynamics.mpm (7 name-valued level attributes over 3 defs, plus two unresolvable `-` placeholders); SURVEY.md:882-887
- **Proposed fix:** State the population as an explicit algorithm in RESOLVED-1. Recommended (it is the only reading under which element-identity dedupe is actually meaningful, and it makes the mixed named/numeric case unbiased): the population is the set of *distinct elements carrying a numeric level* — every `@bpm`/`@transition.to` / `@volume`/`@transition.to` that parses numerically, plus every `<tempoDef>/<dynamicsDef>@value` that is referenced by at least one in-scope level string — each counted exactly once; unresolvable placeholders are excluded entirely (they are already skipped for writing). Then recompute §8's dynamics and tempo bounds from that rule so §8 and §7 agree.

### [MINOR] "Detect a non-numeric attribute" must use the renderer's parseFloat semantics, including def-lookup-first, or applier and renderer disagree on what a string level is

- **Claim:** DESIGN.md:356-357 says "The applier must detect a non-numeric attribute, skip it, and report it". The renderer's actual classifier is: def lookup FIRST, then `parseFloat`, then 100.0 (TempoStyle.ts:50-57, DynamicsStyle.ts:50-55). Two consequences a strict `Number()`/regex classifier gets wrong: `bpm="120bpm"` renders as 120 (parseFloat leniency, already flagged for rubato at SURVEY.md:1388-1393) but a strict check would classify it as a string level and skip it, silently dropping it from both the center and the write set; and a `<tempoDef name="120" value="60"/>` SHADOWS the numeric reading of `bpm="120"` because `style.getDef(tempoString)` runs before `parseFloat`.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/mpm/elements/styles/TempoStyle.ts:50-57; src/mpm/elements/styles/DynamicsStyle.ts:50-55; DESIGN.md:353-358
- **Proposed fix:** Specify the classifier verbatim in §7.1/§7.2: "resolve the string against the in-scope styleDef first; if it resolves, it is a def reference (skip the instruction attribute, transform the def); otherwise `parseFloat` it — non-NaN means numeric and writable, NaN means unresolvable (skip + report)."

### [MINOR] Navigation cost: Element.query() serializes and re-parses the whole subtree per call, so the raw applier must navigate with getChildElements, not XPath

- **Claim:** Answering question (2)'s cost half: pure XML-tree navigation is cheap only if it avoids `Element.query`. `query` serializes the subtree with `toXML()`, re-parses it with DOMParser, runs xpath against the throwaway copy, and maps each hit back by walking a root-relative child-index path (XomTypes.ts:653-692, :726-751). `Header.parseData` (Header.ts:76) and `Dated.parseData` (Dated.ts:63-65) each pay one such round trip at construction. A raw applier doing per-instruction style or def lookups via `query` would be O(document) per lookup. `getChildElements()`/`getFirstChildElement()` (XomTypes.ts:605-627) are O(children) over an in-memory array and are the correct tool. Second-order note: Header and Dated discover styles and maps with `descendant::`, so a direct-child-only raw walker is a strict subset of what the parser considers a map/style — identical for well-formed MPM, divergent for nested ones.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/xml/XomTypes.ts:653-692, :726-751, :605-627; src/mpm/elements/Header.ts:76; src/mpm/elements/Dated.ts:63-65
- **Proposed fix:** Add one line to D-A: "the applier navigates with getChildElements/getFirstChildElement only; Element.query is O(subtree) per call and must not appear on a per-instruction path."

### [MINOR] §7.1's global-map aliasing hazard does not exist under D-A's own architecture

- **Claim:** DESIGN.md:374-377 states "Parts without their own map fall back to the **same** global `TempoMap` object, so a walker that visits global + every part scales it once per part … Deduplicate by `Element` identity." That is true only of a walker built on `Performance.resolvePartMaps` (Performance.ts:599-627, `?? globalMaps.tempo`). D-A's applier locates maps through `Dated.getMap`, and a `Dated` indexes only maps physically under its own `<dated>` (Dated.ts:59-69), so a part without a `<tempoMap>` element returns null and the global map is visited exactly once. The same holds a fortiori for a raw child walker. Element-identity dedupe IS still needed on the def side (one def referenced from several maps), but the instruction-side hazard as stated is an artifact of a helper the design does not use — and stating it invites an implementer to reuse `resolvePartMaps`, which would then also drag in the renderer's per-part header resolution.
- **Evidence:** /Users/nielspfeffer/Projects/meico-ts-exag/src/mpm/elements/Performance.ts:599-627; src/mpm/elements/Dated.ts:59-69, :123-125; DESIGN.md:374-377, SURVEY.md:331-336

## Lens: api

**Verdict:** SOUND-WITH-FIXES, but the fixes are not cosmetic and the weak layer is precisely the one my lens covers. The mathematical core (§1's single transform principle, the seven RESOLVED decisions, the registry's per-attribute evidence) is genuinely strong and survives adversarial reading — RESOLVED-2's joint-trim reparameterization and RESOLVED-6's site discipline in particular are correct and well-argued. What does not survive is the contract layer between that core and its consumers. Three defects are blocking as written: (1) at least three report obligations, including the whole of R6(b) for `accentuation`, require MSM data that R1 forbids as an input — the accentuation estimate needs the MSM's `timeSignatureMap` (MetricalAccentuationMap.ts:140-165), and §8:898-902 asserts the applier has \"already parsed\" note lengths it never sees; (2) R6(b)'s velocity-offset estimate is undefinable for `articulation` because the contribution is affine in the note's incoming velocity (§7.4:534), and R6(b)'s enumeration omits `imprecision`, whose dynamics domain the design itself says adds an unclamped velocity offset — so R6(c)'s \"the caller judges overflow from the report\" cannot be honoured; (3) spotlight's scale scope is specified three times and twice contradictorily (§1.1:62-63 and §7.2:425-427 say local, D-I:286 says global), and both answers misbehave on plain MEI exports. Beyond those, `ExaggerationReport` is an empty interface with a five-item comment standing in for roughly twenty-six obligations scattered through §7, with no site-identity vocabulary and a tri-state that cannot answer R4's own question; CAMPAIGN invariant 6's byte-identity claim is false at the facade because RULE F2a strips the XML declaration every fixture MPM carries; and RESOLVED-7's \"for a fixed seed, the same render\" is contradicted by SURVEY.md:3728-3735, src/api/types.ts:76-83 and CHARTER.md's own parity note — a claim that matters because mlign adopted R1-R6 for training-data augmentation. The option surface is close to minimal but hides three unnamed constants (§7.4's minimum note length, §7.6/§7.10's positive epsilon, R6(a)'s [1,127] — which also silently narrows mlign's stated [0,127]), and §8's validation rule rejects s ≤ 0 on a stated ground that §1's own definition falsifies. None of this overturns the design's direction; all of it should be written into §4 and §2 before W2 begins, because W2's applier is what will hard-code the answers otherwise.

### [BLOCKER] Three R4/R6(b) report obligations need MSM data that R1 forbids as an input

- **Claim:** The design mandates report fields that cannot be computed from the MPM alone, while R1 (DESIGN.md:78-79) makes the MPM the only input. (a) §7.5 requires the accentuation velocity-offset estimate to be `scale · max|getAccentuationAt(beat)|` "over the reachable beats" (DESIGN.md:583, 600-603); the beat argument is `1.0 + ((noteDate − tsDate) % tickLengthOfOneMeasure)/ticksPerBeat`, where tsDate/tsNumerator/tsDenominator come from the MSM's `timeSignatureMap` and noteDate from the MSM score. (b) §7.2:438-440 requires reporting levels as "present-but-inert" because "notes before the first instruction are hardcoded to 100.0" — whether such notes exist is MSM knowledge. (c) §8:898-902 says the ornament-frame cap "depends on values the applier has already parsed" — those values are `duration.perf` on MSM notes, which the applier never sees. So R6(b) is not implementable for `accentuation`, and R4's inertness verdicts for (b)/(c) are unobtainable.
- **Evidence:** DESIGN.md:78-79 (R1), :583, :600-603, :438-440, :898-902; src/mpm/elements/maps/MetricalAccentuationMap.ts:140-165 (tsNumerator/tsDenominator/tickLengthOfOneMeasure read from the passed timeSignatureMap); src/mpm/elements/Performance.ts:476, 639, 705-707 (that timeSignatureMap is collected from the MSM); SURVEY.md:2383-2386
- **Proposed fix:** Split the report into what the MPM can prove and what it cannot. Either (i) drop these three obligations to a *document-relative* form the MPM does support — for accentuation report `|scale'| · max|getAccentuationAt(b)|` over the def's own declared `@beat` anchors plus a `beatsUnverifiable: true` flag, and drop (b)/(c) entirely — or (ii) add an explicitly optional second input `msm?: XmlText` used *only* to compute report estimates (never to transform), documented as an R1 carve-out for measurement, with the report field spelled `null` when it is omitted (RULE N4).

### [BLOCKER] R6(b)'s velocity-offset estimate is undefined for `articulation` and omits `imprecision`, so R6(c) cannot be honoured

- **Claim:** R6(b) promises "the largest |Δvelocity| the scaled attributes can contribute" per velocity-touching dimension, and R6(c) makes cross-dimension overflow "the caller's call, made on the report". For `articulation` the design itself states the contribution is affine in the note's incoming velocity — `v' = (v·r) + c` (DESIGN.md:534) — so no finite MPM-only maximum exists (any bound would have to assume v ≤ 127, i.e. invent the magic constant C2 forbids). ## Lens: musical

**Verdict:** SOUND-WITH-FIXES, but with two blockers that must land before W2. The core is genuinely strong: the single scale-space principle (T with T(neutral)=0) is the right generalization, and the per-attribute neutral determinations in §7 are unusually well grounded — every one I spot-checked against SURVEY's renderer citations (dynamics curvature/protraction proved neutral by Bézier cancellation, rubato intensity's exponent group, accentuation@scale's `velocity + accentuation·scale` site, asynchrony's pure additivity, RESOLVED-2's joint trim) is musically as well as mechanically correct, and the exclusion of rubato@frameLength, accentuationPatternDef@length, dates and enums is properly argued. What is not sound is the layer above the attributes. (1) Spotlight is specified three incompatible ways across §1.1, D-I and §7.2, and neither candidate scope delivers §1.1's own stated musical intent for it — under local scope it is a provable no-op on the MEI corpus (and has no legal write site there at all, since D-C forbids numeric rewrite of named levels), under global scope it deletes the piece's expressive profile including the spotlighted material; D-I also never restates the element-type→dimension mapping that the §3 ornament split now requires. (2) §8's tempo range is arithmetically wrong by roughly a factor of two in the exponent — its own ladder derivation yields s ≈ 1.8, not 4, and s = 4 renders the project's own tempo.mpm at 27 and 427 bpm — because the range was inherited from the prototype's local-scope semantics and never re-derived for the global scope §1.1 introduced (the dynamics row, by contrast, did the arithmetic correctly, which is what makes the tempo row diagnosable rather than merely debatable). Beyond those, the dimension granularity is drawn along implementation lines rather than musical ones in four places — level vs curve shape in tempo/dynamics, frame width vs spacing curve in ornamentTiming (where §8 already prescribes two ranges for one factor), and four perceptual domains fused in imprecision — and one exclusion, movement@curvature/@protraction, is carried by a rationale (D-G, "controller state") that applies to position and not to the curve parameters, against SURVEY's explicit "MEANINGFUL … a genuine expressive axis" verdict and the design's own admission of the mathematically identical dynamics pair. Finally, RESOLVED-6's decisive rationale is refuted by §8's own row: `ornamentDynamics` has no live site on MEI-derived documents either way, and the design should say so and report the dimension inert rather than shipping a knob that cannot move. None of these require abandoning the framework; all are fixable within it.

### [BLOCKER] Spotlight's scope is specified three mutually incompatible ways, and the §1.1/§7.2 reading makes it a guaranteed no-op on the corpus the design calls dominant

- **Claim:** §1.1 says local scope "is what `spotlight` wants"; D-I says spotlight "Uses global scope like everything else"; §7.2 asserts "local scope (which D-I gives `spotlight`)". All three cannot hold. The choice is not cosmetic: under local scope constant instructions are fixed points (`transitionTo === volume` is the renderer's own identity), so on a piecewise-constant map — the shape §1.1 itself identifies as "the common case for mpmify-generated and inferred performances" and which the reference fixture `dynamics.mpm` exhibits (five constant `<dynamics>` and one transition) — spotlight attenuates nothing at all. If the conductor prefers to keep two scopes, then D-I must say `local`, §1.1 must drop the claim that local achieves anything on constant maps, and the report must classify `dynamics`/`tempo` as `inert` for every spotlight run on a name-valued or all-constant map.

### [BLOCKER] §8's tempo sampling range (0.25 … 4) is arithmetically inconsistent with its own derivation and produces unplayable tempi on the project's own reference fixture

### [MAJOR] The global centre's population is occurrence-weighted and contaminated by transition targets and converter duplicates, so exaggerating one gesture shifts the base tempo/dynamic of the whole piece

## Lens: math

**Verdict:** SOUND-WITH-FIXES. The architecture is right: one formula x' = T⁻¹(s·T(x)) per attribute, a neutral proved from the renderer rather than from the spec, RESOLVED-2's reparameterization of the rubato window into a total trim, and RESOLVED-1's single performance-wide center are all correct moves, and the algebra the design actually shows is correct (I re-derived the independent-map crossing equation ee^s + (1−ls)^s = 1 and confirm s ≈ 1.357 for .4/.6 and s ≈ 6.58 for .1/.9; the joint trim's ratio split does compose exactly in ℝ; the ornamentDynamics degree-1 estimate max(|from'|,|to'|)·scale is the right bound). What is unsound is the register in which the guarantees are stated. Three of the design's headline claims — "P2 composition is exact everywhere", "the bounds can never cross at any s", "s = 1 performs zero writes" — are theorems over ℝ asserted as contracts over IEEE-754 doubles and over a pipeline that clamps and skips; each is refutable with concrete numbers, and in two cases (RESOLVED-2's minimum-gap clamp, meanTempoAt's epsilon) the design dropped a guard the survey had stated as mandatory, precisely because the new transform was believed to make it unnecessary. The most serious gap is not a formula error at all: there is no input-domain validation gate, so XML-legal values that the renderer today tolerates benignly become NaN under exaggeration and NaN escapes every clamp in the renderer. None of this requires a redesign — every finding is fixable by adding a guard, narrowing a claim, or moving a constraint from prose into the registry — but the exactness claims must be retracted or made conditional before W2 codifies them as property tests, because as written the tests will either fail or be silently weakened to the point of proving nothing (RESOLVED-3's Tier 1, which tests the empty factors record instead of s = 1, is already an instance of that drift).

### [BLOCKER] The R6(a) [1,127] clamp destroys center invariance, so "P2 composition is exact everywhere" is false inside the documented sampling range

- **Claim:** RESOLVED-1's whole justification is that the performance-wide geometric center is invariant under the transform (geomean of {μ(xᵢ/μ)^s} = μ), which makes a second application reuse the same center. The R6(a) clamp introduced by RESOLVED-4 is applied AFTER the transform to exactly the attributes that constitute the center population (`@volume`, `@transition.to`, `dynamicsDef@value`). The moment one clamp fires, the output population is no longer the image of the input population under the map, its geomean is no longer μ, and exaggerate(s₁)∘exaggerate(s₂) ≠ exaggerate(s₁·s₂). §8's own dynamics row admits the clamp starts firing at s ≈ 1.8, i.e. inside the recommended sampling range 0.25…2.5, so this is the normal case, not an edge.
